# LLD-011: Runtime Table Update — Phase 0 Detailed Design

**Date:** 2026-10-28  
**Status:** Draft — internal processing contract, implementation not complete  
**Parent baseline:** [SRS-011](SRS-011-runtime-table-update.md), [HLD-011](HLD-011-runtime-table-update.md)  
**Design decisions:** [DDR-011](DDR-011-runtime-table-update.md) D-P0-01..08

## 1. Design Boundary and Existing Touchpoints

The data names used below denote **logical records inside the module** and are not proposals for new public classes or APIs. Existing public methods and the proto/SHM layouts are kept. Source changes and implementation plans are not deliverables of this document.

| Existing touchpoint | Intent of the internal change |
|:--|:--|
| [O generation and serialization path](../../timpani-o/src/global_scheduler.cpp) of `GlobalScheduler::build_table()` | Copies the confirmed model and generates and validates a candidate from it. Side effects of the existing generation path are also confined to the candidate |
| [O RecoveryService](../../timpani-o/src/recovery_service.cpp) | In Phase 0, connects `RECOVERY_STOP` to the single-candidate removal `full_table` path and replies after confirming the correlated ACK (`RecoverySignal` is not sent) |
| [O NodeStream](../../timpani-o/src/orchestrator_service.cpp) | Links one attempt's context to the existing push_full_table and result handling |
| [N receive](../../timpani-n/src/grpc/node_client.cpp), [apply callback](../../timpani-n/src/main.cpp) | After parsing and pre-checks, an inactive candidate is prepared. The current up-front deletion and affinity changes SHALL NOT be made |
| [BpfLoader](../../timpani-n/src/bpf_loader.h), [BPF](../../timpani-n/src/bpf/timpani.bpf.c) | Connects the actual TT configuration bank to kernel selection. No new CBS path or redesign |
| [TimerMaster](../../timpani-n/src/timer_master.h) | Internal candidate handover of set_schedule_table, boundary selection in the resident loop, and non-RT result confirmation |
| [SHM/app](../../sample-apps/src/libttsched.h), [consumer](../../sample-apps/src/libttsched.c) | Keeps the layout; strengthens publication order and read/wait rechecks |

Success is not judged from the return value alone of current void methods such as `set_schedule_table()` and `apply_table_update()`. Completion is confirmed from the internally recorded table context, boundary, actual kernel selection, and publication state. If adding a public method becomes necessary for this, separate approval is obtained before implementation.

## 2. Internal Data and Ownership

| Logical record | Contents | Ownership and lifetime |
|:--|:--|:--|
| OConfirmed | Current confirmed model and full table | O non-RT path. Replaced only after a matching successful ACK |
| OAttempt | node/table ID, operation/target, candidate model/table, progress status | One per node. Kept from transmission through result handling |
| NPrepared | Immutable slot array (including per-core next-slot offsets), isolated CPU mask in use, per-task assigned CPU and PID/hash mapping, removal set, SHM image, bank number, E/H/G/T | Created on the N non-RT path. SHALL NOT be released before RT use ends and old references are cleaned up |
| KernelControl | Active bank, TT handover gate, per-bank reference records | Aligned shared control region prepared at load time. Atomic access from BPF and userspace |
| ApplyCompletion | Preparation token, whether applied, planned/actual time, cleanup result | RT publishes only fixed-size fields. String construction, logging, and ACK are on the non-RT path |

The `table_id` string is not copied in RT. It references the context already built from the preparation token. The slot sort key is fixed as `(offset_ns, cpu, workload_id_hash, task_id_hash, slot_idx)`, and `slot_idx` follows the position in the snapshot generated by O. Each slot's next start time points not to the adjacent slot in the whole array but to the next slot on the same `cpu` (the last slot points to the first slot of that core after `H`). The design does not go as far as proving input-order independence of the global generation result.

The SHM image is built per unique task. The indices and counters of retained tasks are preserved, and the names at removed positions are cleared. A new task uses an empty index, and the counter of an existing waiter is neither increased nor reset as a publication event. `n_tasks` is the highest occupied index plus 1, and it is 0 for CLEAR. Mapping conflicts, hash collisions, and capacity overflows are rejected before publication.

## 3. L-P0-01 — O Input and Candidate Generation

1. If a request is already in progress for the node, it is rejected through the existing failure path. No queue is created.
2. On the preconfigured isolated CPU set (`0..63`, no duplicates) and on the E and global H of the known confirmed baseline, OConfirmed is copied and the workload set of the test input is reflected. Active tasks present in the confirmed table keep their existing assigned CPU fixed, and new workloads are assigned to unused isolated CPUs first (or, when all are occupied, to the CPU with the least load). The same task identity is not reused for a different task during a test run.
3. For a non-empty candidate, the minimum LCM of the node-wide TT periods is computed and checked to ensure the periods are harmonic and the LCM divides the confirmed execution frame `H`. This minimum repeat cycle does not replace `H`: O retains the baseline `E/H`, expands slots over the same `H`, and preserves retained tasks' repeated slots. The existing generation and schedulability checks and serialization are performed on that fixed-frame candidate. For an empty candidate, the minimum LCM is undefined and the baseline `E/H` is retained. The candidate is discarded if a single task is distributed across multiple CPUs, a retained task's assigned CPU moves, retained items change under ADD/REMOVE, or conversion or capacity checks fail.
4. A non-empty unique table ID is assigned. Every candidate, including CLEAR, carries the confirmed `E/H` and node ID; CLEAR has empty partitions.
5. The existing NodeStream sends the full_table, and OAttempt is kept. OConfirmed is not changed by transmission success alone.
6. `EnforceRecoveryPolicy(RECOVERY_STOP)` resolves the target workload (by identifier or hash) and registers it through the same single-candidate REMOVE path (a table with empty partitions if no workloads remain). It does not send `RecoverySignal`. On a conflict with an in-progress candidate, a nonexistent target, or a validation failure, it returns failure immediately. Once the candidate is registered, it waits, within a finite wait deadline (5 s), for the result of that attempt to settle, and returns success and keeps the session only when removal of the target is confirmed in the confirmed model (up-front rejection, session interruption, or deadline expiry returns failure).

**P0-T01 connection approval (2026-10-29):** The existing path is preserved, and this contract applies only with `--runtime-table-update-phase0`. Addition of the two connection methods `SchedInfoServer::EnablePhase0` and `PushPendingTables` has been approved. Activation is performed before service start, and the existing main non-RT loop sends the unsent candidate exactly once. The ACK and connection-loss callbacks share the lifetime of the internal state. Because the candidate's send status is recorded and the lock is released before sending, an ACK received before `Write` returns can also be handled. Even while waiting for the first connection, there is only one candidate, and subsequent requests are not stored.

The additional test processes SHALL also be creatable, registrable, and able to wait in advance. Local preparation is not compensated by changing policy/affinity during a table update. Test preparation uses the existing node and workload startup procedures and does not let applications set kernel attributes themselves.

## 4. L-P0-02 — N Pre-Checks and Rejection

| Check item | Handling |
|:--|:--|
| Receive context | Confirms the currently authorized connection, the target node ID, and a non-empty table ID |
| In-progress candidate | While one candidate is being prepared, handed over, or cleaned up, an additional command receives a failure response with no state change |
| Test scope | Only TT is allowed. CBS, non-TT models, distribution of a single task across multiple CPUs, CPU movement of retained tasks, changes to the baseline E/H, and delta paths are rejected |
| Retained workload | Preserves the full slot parameters of the active baseline (task, offset/duration/deadline, CPU, current_limit, layer) and the repeat count. Cases that differ only in input order or slot_idx are allowed; changes in task composition are rejected |
| Values/representation | Candidate H equals confirmed H; candidate periods form a harmonic set whose minimum LCM divides H; lossless ns conversion of times; overflow in sum and boundary calculations; slot range check within `[0,H)` |
| Local references | Whether the isolated CPU mask (`0..63`) covers all CPUs in use; uniqueness and liveness of task names/PIDs; consistency between identifiers and hashes |
| Capacity | Minimum upper bounds of the TT map, task map, and SHM in the actual build. Unique tasks and repeated slot counts are calculated separately |

N does not perform overlap checks between slot pairs, CPU reassignment, or schedulability analysis. Even if the time range and format are correct, responsibility for schedulability lies with O.

In this phase, the active workload tracking map, BPF configuration, and SHM are not deleted or overwritten. On a preparation failure, only the candidate-only registrations/maps are reverted and discarded; after confirming that the existing model, execution, and publication are unchanged, `success=false` and the reason are sent. Errors after the apply gate has been closed are not reported as covered by this up-front rejection guarantee.

**P0-T02 connection approval (2026-10-29):** N also applies these checks only under `--runtime-table-update-phase0`, and the default path is kept. Without changing `NodeClient` or the public API, the existing callback registers `full_table` as one attempt. The pre-checks and `NPrepared` assembly are performed by the internal module `phase0_prepare` in the existing main non-RT loop. This module reads the isolated CPU mask once at startup from cgroup v2. Candidates that pass are handed to the existing immediate-apply path until P0-T03..T06 are in place, so during this period the boundary transition and SHM publication contract in §6~§8 do not yet hold.

## 5. L-P0-03 — BPF Inactive-Bank Preparation and Reference Lifetime

The two banks, TT slots and TaskMeta (each task's `assigned_cpu` is set to the assigned CPU of that task's record), use the same active selector. The existing structures are kept, but the candidate write target of BpfLoader and the lookup target of BPF are connected to the actual banks. A method that only has the current userspace index toggle is insufficient.

- The non-RT preparer clears and fills the inactive bank only when it is not used in an RT context and its kernel reference count is 0. If this cannot be confirmed, it does not touch the active state and does not complete preparation.
- The BPF processing section reads the selector, acquires the corresponding reference, and then rechecks the selector/gate. If it has changed, it does not use that bank's data and returns the reference. On success, the section reads the slots and metadata from the same bank and returns the reference on every exit path.
- The per-core count of runnable TT tasks (`tt_runnable_count_map`) is managed by 64-bit atomic increments and decrements, and both enqueue and stopping count against the task's assigned CPU.
- When the TT handover gate is closed, neither a candidate nor a previous TT job is newly run. A woken TT task is kept in an assigned-CPU holding queue that no select/enqueue/dispatch path consumes while the gate is closed; it is not inserted into `SCX_DSQ_LOCAL_ON` or `SCX_DSQ_GLOBAL`. After boundary publication completes and the gate opens, only tasks present in the new active table may be released for TT execution according to that table's slot schedule. Tasks removed by the update are removed from the holding queue and excluded from TT release; they are cleaned up under §8 without dispatch.
- The mutable TT fields of the new bank are prepared for the new run, but `tt_runnable/activation_ns` of the active bank is not initialized during preparation. When the runnable state is actually entered, `activation_ns` is recorded, and deadline misses relative to the assigned CPU are judged only for runnable TT jobs. The end of the old run is confirmed only at a TT-free handover in which no task is running.
- After the boundary handover, once the old timer context and kernel references have ended, the old bank and removal registrations are cleaned up on the non-RT path. The next request is not accepted until cleanup completes.

The memory ordering between reference acquisition, recheck, and cleanup is verified by tests on the target BPF/userspace. The shared control region is prepared at load time, and the required atomic support and alignment are checked in advance. No new dependency or public ABI is created. No CBS runtime state, new preservation algorithm for the fault-monitoring state, or general retirement state machine is introduced.

## 6. L-P0-04 — Boundary Handover on the Fixed Grid

The received `hyperperiod_us` SHALL represent the confirmed execution frame `H`, unchanged from the baseline. `H_ns = uint64(hyperperiod_us) * 1000` is computed within the verified range. `T = E + k * H_ns` is selected so that it is later than the candidate preparation time and allows all old TT slots to complete. Inputs that change `E/H`, cause overflow, or cannot produce a valid grid are rejected before activation.

| Interval | Owner and action | Invariant condition |
|:--|:--|:--|
| Before handover | Non-RT prepares NPrepared, inactive BPF, and SHM image | Active execution and publication unchanged. If late, a later boundary is selected |
| Old slot completion G | The resident timer atomically records that the last slot on all isolated CPUs has completed and that handover is possible | Not complete if any involved CPU still has an in-progress TT job or pending execution, or if old references remain |
| `[G,T)` | On the non-RT path, confirms TT-idle and gate-closed state on all involved isolated CPUs (`active \| next` mask); invalidates the SHM generation and writes the image; selects the new BPF bank; resets the current slot of each involved CPU to `SLOT_NONE` and that core's first firing time (idle if there is no slot) | No old TT job on any involved CPU, no candidate TT execution, and the new SHM is not yet valid |
| Boundary T | RT checks the preparation-complete token with acquire ordering, selects the new context, validates the even generation/magic, and releases the TT gate | Before any actual firing, the kernel, timer, and app all use the same candidate. Additional work is limited to a fixed number of memory operations |
| After boundary | Fires new slots, passes completion records to non-RT, cleans up old items, and confirms results | A success ACK does not precede this confirmation |

SHM data copying, BPF map updates, task lookup, sorting, thread creation/join, cleanup, and string logging are not performed in RT. Boundary validation in RT is handled by atomic stores to the shared control values secured at load time. The existing control path needed for actual slot firing SHALL also maintain consistency between the candidate and active banks.

If preparation does not reach the boundary after the start of handover, it is not treated as success. This is a test-precondition failure, and the system does not apply the table at an arbitrary time or restart with a new epoch. Automatic restoration and retry are not designed. Interruption by the test harness is not interpreted as guaranteeing a product safety stop.

CLEAR activates the empty context in the same way. The resident loop waits on the H grid without slots and handles subsequent ADD/REPLACE. The last task already executed is allowed to complete, and TT metadata and tracking entries are cleaned up, but policy/affinity is not changed.

**P0-T04 connection approval (2026-11-02):** The handover rules are placed in the internal module `phase0_handover`, and TimerMaster connects the actual kernel and SHM touchpoints. The coordinator publishes the commit only when at least 1 ms remains until T, and it checks TT runnable and active-bank refs before and after closing the gate. If the quiescent state cannot be confirmed, the application is deferred for up to 8 boundaries and then rejected before it is applied. At each boundary, the RT thread checks the handover state and switches to the prepared candidate with a fixed number of atomic operations. If the candidate is not ready by T after commit, the failure is recorded and firing stops. Addition of the public methods `TimerMaster::enable_phase0` and `apply_phase0_table`, and of `BpfLoader::kernel_control`, `tt_runnable_count`, and `select_staged_bank`, was approved. Connection of the main non-RT loop and cleanup of old state are done in L-P0-06 (P0-T06).

## 7. L-P0-05 — SHM Publication, Reading, and Waiting

### 7.1 Writer

1. Non-RT preparation completes the new image and index mapping. The stable generation `g` is even, and overflow of `g+2` is checked in advance.
2. At a TT-free handover, `generation=g+1` and `magic=0` signal that publication is in progress. After write ordering is ensured, metadata such as names and n_tasks is recorded.
3. Counters are preserved. Names of removed tasks are cleared, and new names are placed uniquely. Publication does not increase all counters or issue a global futex wake.
4. At boundary T, after BPF and timer preparation has completed, RT publishes `generation=g+2` and a valid magic with release ordering. TT firing is permitted only after that.

The initial common publication path also uses a valid even generation. This is not a new requirement for an initial startup test; rather, it is a condition for creating a baseline publication that runtime consumers can interpret.

### 7.2 Consumer

- A read consists of a generation/magic check with acquire ordering, an atomic copy of the required fields, and a final generation/magic recheck. The data is used only when both checks show the same stable generation. Copying shared fields is not assumed to be safe with ordinary memcpy/volatile alone.
- If the publication is invalid or odd, or the generation has changed, partial values are discarded. The existing `-1`/recheck contract is used, and no unbounded busy-spin is performed. Quantitative guarantees for persistent invalidity are a Phase 1 target.
- Before futex waiting, the task's own identity, index, and counter are recorded; after the wait, the valid publication is interpreted again. If the task has been removed, `-1` is returned; if the position has been reused by another task, that wake is not consumed.
- A successful futex return or EAGAIN alone is not treated as a job. Zero is returned only after the task's own actual counter change is confirmed. If it was woken by a publication or signal but the counter is unchanged, it keeps waiting for the actual job.
- Even when a retained task's actual slot overlaps a generation change, a job is not produced unconditionally. The actual firing of the same task/counter is confirmed. A general guarantee of no loss of the first job is a Phase 1 verification target.

The current ABI's 0 is kept as an actual job, and -1 as the result meaning do not execute and recheck. The test configuration that uses the updated libttsched together with N is recorded, and old consumers are not assumed to satisfy this rule.

**P0-T05 consumer connection approval (2026-11-02):** The writer and consumer rules are placed in the internal header `sample-apps/src/ttsched_shm.h`, which is not installed. This header handles odd/even generation publication, byte-wise name copying, generation rechecks before and after the copy, and wake determination. The futex wait is injected as a function. Only when the task's own counter has increased in the forward direction at the same position as the earlier snapshot is it a job. If the position has changed, or the counter is unchanged or has been reset, it waits again. An invalid publication and a non-publication (removal or CLEAR) yield `-1`. The existing TimerMaster common publication also uses the same generation rule. However, the existing publication wake remains until the publication without counter increment in §7.1 and the boundary-T validation are applied.

## 8. L-P0-06 — Removal and Result Completion

The removal set is computed on the non-RT path as the difference between the previous and candidate workload and task sets. A recovery STOP also follows the same single `full_table` attempt and boundary cleanup procedure, without a separate direct `RecoverySignal` deletion. After a normal handover, once old references have ended, TT entries, task metadata/registrations, workload tracking, app entries, and candidate-only references are cleaned up. Retained items are not deleted and then re-registered. Containers are not terminated, and policy/affinity is not restored.

Non-RT result processing confirms actual handover completion for the same preparation token, the selected bank/context, the valid SHM generation, and removal cleanup. After confirmation, the existing `send_table_applied(table_id, true, error)` path is used. No new wire code convention for `error` is created.

O uses only results that match the current node/table ID for confirmation. On up-front rejection, the candidate is discarded and the confirmed state is kept. After switchover, errors, mismatched ACKs, connection loss, and unconfirmed outcomes are recorded as test errors, and subsequent submissions are blocked. Restoring the previous state or automatic convergence is not implicitly assumed.

**P0-T06 connection approval (2026-11-02):** The attempt order and ACK judgment are placed in the internal module `phase0_attempt`, and main connects the TimerMaster, BpfLoader, SHM, and FaultMonitor touchpoints through ports. After up-front checks, the main non-RT loop waits for boundary application through `apply_phase0_table`. It then confirms the change of the active bank, the even SHM generation and magic published in this attempt, and `actual_apply_ns ≥ T`. The old bank is cleared as a whole once its references have ended, with retries at 1 ms intervals for up to 100 ms. The tracking map is rebuilt from the new table, and FaultMonitor is initialized according to the existing full-table rule and then populated with the new limits. The success ACK is sent only after all of these phases are complete. A rejection made before the active state is changed is reported as `success=false` with the reason. After the start of handover, a failure, a confirmation failure, or a cleanup timeout is recorded as `trial_failed` without an ACK and without restoration, and the N connection is dropped. The attempt remains busy, and O aborts the test on connection loss.

## 9. L-P0-07 — Lock, Memory, and Resource Discipline

| Path | Allowed | Prohibited |
|:--|:--|:--|
| Non-RT creation/preparation/cleanup | Existing serialization and locks, vector/map preparation, BPF updates, resource cleanup | Up-front destruction of active structures; waiting for boundary completion while holding a lock |
| RT boundary/slot | Reading of pre-prepared data, fixed-size atomic publication, waiting for absolute time and existing firing | Dynamic allocation, join, gRPC, file logging, unbounded search/retry, blocking locks |
| Application | Existing futex wait, valid lookup, no firing when invalid | Treating a publication notification as an actual job |

If the existing lifecycle lock of `TimerMaster` is needed, it is acquired before the schedule lock, and neither is brought into the RT loop. No lock is held across scheduling decisions. Boundary waiting is performed after the preparation/tracking locks are released. Shared atomic values are implemented with explicit alignment, size, and acquire/release ordering, and are verified on the target.

Only one fixed candidate, two configuration banks, and the current SHM upper bound are used. The basic normal contract of returning resources after removal or failure is verified, but a comprehensive analysis of long-running leaks, capacity expansion, and priority inversion is not added as a prerequisite task.

## 10. L-P0-08 — Test Touchpoints and Traceability

Unit tests cover O candidate separation, N pre-checks and side-effect-free rejection, sorting/time calculation, SHM generation/control wake, and result correlation. Overall success is not declared on the basis of a BPF stub or direct injection into N alone. Target-hardware tests include O's actual generation/transmission and N's BPF/timer/app execution.

The test log links the preparation, handover, and actual completion tokens and table ID, the planned boundary, the actual completion time, bank/generation, task PID/firing, and reason/result. RT updates only prepared record slots, and file output is performed on the non-RT path. The start criteria for each test are rechecked, and finite test-wait limits are recorded. If hardware verification was not performed, it is marked separately as unverified.
