# REQ-011: 런타임 Schedule Table 갱신 — 요구사항 정의서

**작성일:** 2026-09-29  
**최종 수정:** 2026-10-28 (Phase 0/1/2 도입, Phase 0 기본 동작 범위·수용 기준·후속 문서 작성 기준 분리)  
**상태:** Draft  
**현재 설계 기준:** Phase 0 — Runtime Table Update 기본 동작 확인  
**작성자:** Human (Lead Architect) + AI  
**상위 요구사항:** SRS-000 `REQ-FUN-012`  
**관련 문서:** DDR-002(스케줄링 아키텍처), DDR-003(인터페이스/프로토콜), DDR-005(BPF 스케줄러), DDR-006(통신), DDR-007(TT/CBS), DDR-011(런타임 테이블 갱신 설계), DDR-012(결함 관리)  
**후속 문서:** SRS-011, HLD-011, DDR-011, LLD-011, implementation_plan. 현재 개정 대상 문서는 모두 **Phase 0 기준**으로 작성하며, 기존 문서 세트의 전체 기능을 현재 구현 범위로 자동 승계하지 않는다(§8.2).

> **문서의 역할.** 본 문서는 **요구사항 정의서**이다. 런타임에 schedule table이 변경될 때 TIMPANI가 *무엇을* 해야 하고 *왜* 그래야 하는지를 이해관계자/시스템 수준에서 규정한다. 프로토콜, 자료구조, 알고리즘은 의도적으로 고정하지 않으며, 이는 SRS-011에서 명세하고 DDR-011에서 결정한다.
>
> **키워드 규약:** **SHALL** = 필수, **SHOULD** = 권고, **MAY** = 선택.

## 1. 목적과 범위

### 1.1 목적

**시스템이 동작하는 중에** TIMPANI의 schedule table을 변경하는 기능을 단계적으로 구현하기 위한 요구사항을 정의한다. 현재는 **Phase 0의 기본 갱신 동작 확인**을 설계·구현 대상으로 삼고, 세부 관리·품질/정확도 향상·기능 확장은 Phase 1, fail-safe 기능은 Phase 2로 분리한다.

기존 요구사항은 최종 목표와 추적성을 보존하기 위해 유지한다. **현재 적용 범위는 §1.5, 현재 수용 기준은 §7.1**을 따른다. 후속 단계의 요구사항 미충족은 Phase 0의 미완료 사유가 아니며, Phase 0 완료가 전체 기능 또는 기능안전 수준의 충족을 뜻하지 않는다.

### 1.2 요구사항 원문

#### 1.2.1 원문 (원형 보존)

> "timpani 동작중에 schedule table이 새로운 작업이 생성되고 이 schedule table을 기반으로 기존의 schedule table이 **대체**되거나, 새로운 작업이 기존의 schedule table에 **추가**되거나, 작업 중 일부가 기존의 schedule table에서 **제거**되거나, 전체 작업의 schedule table이 **삭제**되는 경우가 있고, timpani는 이를 대응해야 한다."
> — 원 요구사항 (Project Leader, 2026-09-29)

원문은 추적성을 위해 원형 그대로 보존한다. 원문은 *어떤 상황이 발생하는지*는 말하지만, 변경의 단위, 테이블의 범위, "대응"이 함축하는 품질 속성, 실패 시 동작은 규정하지 않는다. §1.2.2에서 그 결손을 기록하고, §1.2.3에서 §5로 분해 가능한 형태로 재진술한다.

#### 1.2.2 원문의 모호성과 결손

| # | 원문 표현 | 모호성 / 결손 | 본 문서의 해석 결정 |
|:-:|:--|:--|:--|
| 1 | "새로운 작업", "작업 중 일부" | 단위가 workload인가 task인가 process인가 | 런타임 변경의 단위는 DDR-001이 정의하는 **workload**이다. workload는 여러 task를 포함할 수 있으며, 변경은 언제나 workload 전체에 적용된다. |
| 2 | "작업" | 어떤 스케줄링 계층이 대상인가 | schedule table에 표현되는 것은 **L1(TT)** 과 **L2(CBS)** workload뿐이다. L3/L4는 Linux 기본 스케줄러에 위임되어 테이블 밖에 있다(DDR-002). |
| 3 | "schedule table" | 전역 테이블 1개인가 노드별인가 | schedule table은 **노드 단위** 산출물이다. 배포 수준 변경은 대상 노드별 갱신 1건씩으로 분해된다. |
| 4 | "대체 / 추가 / 제거 / 삭제" | 와이어 연산인가 관측 가능한 결과인가 | **의미론적** 연산이다. 이를 실어 나르는 전송 방식(전체 스냅샷 또는 증분 델타)은 설계 선택이며 결과를 바꾸어서는 안 된다. |
| 5 | *(누락)* | 동작 중인 워크로드의 **파라미터**만 바뀌는 경우(주기, 예산, 데드라인, CPU)가 4가지 중 어디에도 없음 | 다섯 번째 도출 연산 **UPD-MODIFY**로 추가한다(REQ-011-F-046). 별도 와이어 연산인지 UPD-REPLACE로 실현할지는 OI-13. |
| 6 | "대응해야 한다" | 품질 속성 없음: 무중단인가? 원자적인가? 언제 적용되는가? | "대응"을 **무중단, hyperperiod 경계에서의 원자적 적용, 상한이 있는 활성화 지연, 무관 워크로드 무간섭**으로 정의한다(§5.3, §5.4). |
| 7 | *(누락)* | 누가 변경을 촉발하고 누가 테이블을 생성하는가 | 인가된 트리거와 역할 분담 — Pullpiri가 배포를 결정하고, Timpani-O가 테이블을 생성하며, Timpani-N이 이를 실행한다 — 을 §5.2에 규정한다. |
| 8 | *(누락)* | 실현 불가·수신 정보 오류·활성화 중간 실패 시 동작과 각 책임 주체 | 스케줄 가능성 판단은 Timpani-O, 수신 테이블의 노드 적용 적합성 확인은 Timpani-N의 책임으로 구분하고, 거절·복원 동작을 §5.5와 §5.6에 규정한다. |
| 9 | *(누락)* | 테이블 변경 중 동작 중인 애플리케이션이 관측하는 것 | 애플리케이션 관점 동작을 §5.7에 규정한다. |
| 10 | *(누락)* | 변경이 동시에 또는 순서가 어긋나 요청될 때 | 순서·대체·충돌 결과를 REQ-011-F-027, REQ-011-F-029에 규정한다. |
| 11 | *(누락)* | 하나의 논리적 변경이 여러 노드에 걸치고 일부만 수락할 때 | 시나리오 E-06과 REQ-011-F-047로 추가한다. 원자성 경계 자체는 OI-14. |
| 12 | *(누락)* | 변경 결과를 어떻게 관측하고 증적으로 남기는가 | 보고와 기록을 §5.6, §5.8에 규정한다. |
| 13 | *(누락)* | 하나의 갱신이 담을 수 있는 상한이 있는가 | 용량 한계와 수락 시점 거절을 REQ-011-N-004에 규정한다. |

#### 1.2.3 보강된 요구사항 진술(정규화)

아래 재진술은 **전체 단계 완료 시의 목표**이며 §5의 근거가 된다. Phase 0에 모든 성질을 일괄 요구하지 않으며, 단계별 적용 범위는 §1.5와 §5의 단계 표기를 따른다.

| ID | 보강된 진술 |
|:--|:--|
| **SR-01** | 런타임 변경의 단위는 **workload**이며, schedule table에 표현되는 L1(TT)·L2(CBS) workload만이 본 요구사항의 대상이다. |
| **SR-02** | schedule table은 **노드 단위** 산출물이며, 배포 수준 변경은 대상 노드별로 주소 지정된 갱신 1건씩으로 적용된다. |
| **SR-03** | TIMPANI 동작 중에 노드의 schedule table은 **대체**, **추가**, **제거**, **제자리 변경**, **전체 삭제**될 수 있으며, TIMPANI는 이 5가지를 모두 지원해야 한다. |
| **SR-04** | 이 중 어떤 경우도 Timpani-O, Timpani-N, 그리고 변경 대상이 아닌 워크로드의 재시작을 요구하지 않아야 한다. |
| **SR-05** | 변경은 공통 epoch 격자의 **hyperperiod 경계에서 원자적으로** 적용되며, 수락에서 활성화까지의 지연에는 상한이 있고 그 상한을 수치로 명시한다. |
| **SR-06** | 변경 대상이 아닌 워크로드는 데드라인 미스, 잡(주기 실행) 누락, 예산 초기화 없이 계속 동작해야 한다. |
| **SR-07** | 변경은 인가된 트리거에서만 발생하고, 그 결과인 schedule table은 Pullpiri가 제공한 L1/L2 워크로드 정보와 노드별 격리 CPU 리스트로부터 오직 Timpani-O만이 생성하며, 각 갱신은 특정 노드에 주소 지정된다. |
| **SR-08** | Timpani-O는 schedule table의 실현 가능성·스케줄 가능성을 판단한다. Timpani-N은 받은 테이블이 자신을 대상으로 하고, 표현 및 노드 로컬 실행 조건을 만족하는지만 적용 전에 확인하며, 스케줄 가능성을 다시 계산하지 않는다. 어느 단계의 거절도 활성 테이블을 바꾸지 않는다. 활성화 중 실패한 변경은 이전 테이블 복원 또는 정의된 복원 실패 정지 상태로 귀결되며, 부분 적용 테이블은 결코 허용되지 않는다. 연결 단절·재시작 이후에는 빈 테이블을 포함해 의도 상태로 수렴한다. |
| **SR-09** | 모든 변경의 결과는 Timpani-O에 보고되고, 사후 분석에 적합한 형태로 기록된다. |

#### 1.2.4 도출된 갱신 연산

| ID | 연산 | 의미 |
|:--|:--|:--|
| **UPD-REPLACE** | 전체 대체 | 새로 생성된 schedule table이 노드의 활성 schedule table을 통째로 대체한다. |
| **UPD-ADD** | 증분 추가 | 하나 이상의 새 워크로드가 활성 schedule table에 추가되고, 기존 항목은 유지된다. |
| **UPD-REMOVE** | 증분 제거 | 일부 워크로드가 활성 schedule table에서 제거되고, 나머지 항목은 유지된다. |
| **UPD-MODIFY** | 제자리 변경 *(도출, §1.2.2 #5)* | 워크로드 집합은 그대로인 채, 이미 존재하는 워크로드의 타이밍 파라미터가 변경된다. |
| **UPD-CLEAR** | 전체 삭제 | 모든 워크로드가 제거되어 노드의 schedule table이 비게 되고, 노드는 유휴(TT/CBS 없음) 상태로 돌아간다. |

### 1.3 범위에 포함되는 것

아래는 전체 단계의 기능 범위이다. 현재 설계·구현에 포함되는 부분은 §1.5에서 한정한다.

- 동작 중인 노드의 L1 TT 슬롯 테이블 및 L2 CBS 예산 집합의 런타임 변경
- 배포를 결정하고 L1/L2 워크로드 정보와 노드별 격리 CPU 리스트를 공급하는 Pullpiri → schedule table을 생성하는 Timpani-O → 이를 실행하는 Timpani-N으로 이어지는 변경 전파
- 변경의 활성화 의미, 원자성, 격리, 검증, 실패 처리, 관측 가능성
- 이미 실행 중인 TT/CBS 애플리케이션에 대한 변경의 영향
- 하나의 논리적 변경에 대한 다중 노드 일관성

### 1.4 범위에서 제외되는 것

- schedule table 생성 정책 자체(배치, CPU 할당, 실현 가능성 알고리즘) — DDR-004, DDR-007
- Linux 기본 스케줄러에 위임되어 schedule table에 표현되지 않는 L3/L4(NonSafety) 워크로드 — DDR-002
- 결함 탐지 및 복구 *결정* 로직 — DDR-012. 여기서는 schedule table에 대한 *적용 결과*만 다룬다.
- **갱신이 원인이 아닌** 노드 이상 — BPF 스케줄러 상실, 타이머 스레드 장애, 시계 불연속, 파티션 구성 훼손 등. 이들은 결함 관리(DDR-012) 영역이다.

  > **Phase 2 범위 결정.** 일반적인 노드 건강 상태 모델은 도입하지 않는다. 이전 테이블을 복원할 수 없는 실패가 발생하면 노드는 갱신 범위의 **복원 실패 정지 상태**(§2)에 들어가며, 이 상태에서 벗어나는 유일한 경로는 Timpani-O의 전체 테이블 재적용이다. 이 복구 상태 기계는 Phase 0의 구현 대상이 아니다.
- 노드 초기 기동 및 최초 테이블 적재. 런타임 갱신과 메커니즘을 공유하는 부분만 참조한다.
- 시스템 전원 재투입 간 schedule table의 영속성

### 1.5 단계별 구현 범위와 현재 기준

#### 1.5.1 단계 정의

| 단계 | 목적 | 구현 범위 | 완료 판단 |
|:--|:--|:--|:--|
| **Phase 0 — 기본 동작** | Runtime Table Update가 실제로 동작함을 확인 | 제한된 시험 조건(단일 노드, 하나 이상의 격리 CPU, 유지 태스크 코어 고정)에서 테이블 생성·전송·경계 적용·실행 결과 확인(복구 STOP에 따른 제거 포함)의 정상 경로와 최소 입력 거절 | §7.1의 Phase 0 수용 기준 충족 |
| **Phase 1 — 관리·품질·확장** | 운용 가능한 기능으로 확장하고 품질/정확도를 높임 | 요청 관리, 정량적 타이밍·FFI 검증, 애플리케이션 세부 계약, CBS, 파라미터/hyperperiod·격리 CPU 구성 변경, 활성 태스크 코어 간 이동, 코어별 타이머 확장·다중 노드 정상 동작, 인터페이스·감사 기록 | 해당 단계 착수 시 구체화한 SRS와 수용 기준 충족 |
| **Phase 2 — Fail-Safe** | 실패 시 안전한 결과와 복구를 보장 | 활성화 실패·롤백·복원 실패 정지, ACK 미확인·재연결·재시작 재동기화, 복구 STOP 실패 차단·재동기화, 시계 이상, 결함 감시 상태 보존, 다중 노드 부분 실패 처리 | 결함 주입과 복구 시나리오를 포함한 수용 기준 충족 |

단계는 누적된다. 후속 단계는 앞 단계의 정상 동작을 유지하면서 기능을 보강한다. **이관은 신규 구현·검증의 유예이지, 기존 동작이나 안전장치를 제거할 허용이 아니다.** Phase 0에서도 역할 분리, 정상 전환의 테이블 일관성, RT 경로 규율, 인터페이스 변경 승인 제약은 유지한다.

#### 1.5.2 Phase 0의 시험 경계

- **대상:** 단일 노드의 L1 TT 워크로드. 사전 지정된 하나 이상의 격리 CPU에서, 현재 표현으로 정확히 나타낼 수 있는 노드 전역 harmonic 주기와 충분한 여유를 가진 시험 테이블을 사용한다. CBS와 복합 파이프라인은 Phase 1로 이관한다.
- **시간·자원:** 갱신 전후 노드의 epoch, 전역 hyperperiod, 격리 CPU 집합 구성을 고정한다. 각 TT 태스크는 단일 격리 CPU에 배정되며, 갱신 후에도 유지되는 활성 태스크는 기존 배정 CPU에 고정된다(활성 태스크의 코어 간 이동은 Phase 1로 이관). 기존 TT 슬롯은 경계를 넘지 않도록 구성한다. 빈 테이블도 이 시간 기준을 유지하여 후속 테이블을 받을 수 있어야 한다.
- **갱신:** UPD-REPLACE, UPD-ADD, UPD-REMOVE, UPD-CLEAR의 네 가지 결과를 **노드 전체 테이블 스냅샷 한 경로**로 확인한다. 별도 증분 와이어 연산은 요구하지 않는다. 유지되는 워크로드의 파라미터는 바꾸지 않으며 UPD-MODIFY는 Phase 1로 이관한다.
- **입력·역할:** Timpani-O의 기존 입력(워크로드 추가 및 복구 STOP) 또는 시험 경로에서 변경할 워크로드 집합을 제공하고, O가 생성·검증한 테이블을 기존 O→N 전체 스냅샷 경로로 보낸다. N에 시험용 테이블을 직접 주입하는 것만으로 end-to-end 성공을 판정하지 않는다. CPU 정보는 기존 설정을 사용하며 Pullpiri의 CPU 리스트 공급·정상 배포 해제용 신규 인터페이스는 Phase 0의 선행 조건이 아니다(OI-16, OI-17).
- **요청·환경:** 노드당 한 번에 한 건만 처리하고 결과 확인 후 다음 요청을 보낸다. 연결과 시계가 안정된 통제된 시험 환경을 전제한다. 대기열·병합·재전송·자동 복구는 구현하지 않는다.
- **보장 수준:** 데몬과 유지되는 워크로드를 재시작하지 않고 경계 전환 후 의도한 테이블로 실행되는지 확인한다. 지터·최악 지연·잡 누락 0건·예산/감시 상태 보존의 정량적 보장은 Phase 1/2의 별도 검증 대상이다.

활성화 전 확인 가능한 입력·범위 오류는 Phase 0에서도 거절한다. 활성화 도중의 실패나 연결 단절 등 위 전제를 벗어난 실행은 **Phase 0 성공으로 판정하지 않고 시험을 중단하여 원인을 기록**한다. 자동 롤백·안전 정지·복구 보장은 Phase 2에서 다루며, Phase 0을 실차·안전 운용 승인 근거로 사용하지 않는다.

## 2. 용어 정의

아래 용어는 전체 목표에 사용한다. 커밋 창의 수치 상한은 Phase 1, 롤백·복원 실패 정지 상태는 Phase 2에서 상세화하며, 용어의 존재만으로 Phase 0 구현을 요구하지 않는다.

| 용어 | 정의 |
|:--|:--|
| **Schedule table** | Timpani-N이 실행하는, 노드 단위의 L1 TT 슬롯 및 L2 CBS 예산 항목 집합과 그 hyperperiod·epoch |
| **활성 테이블(Active table)** | 노드가 현재 실행 중인 schedule table |
| **후보 테이블(Candidate table)** | 수신/도출되었으나 아직 활성화되지 않은 테이블 |
| **Hyperperiod** | TT 슬롯 패턴의 반복 주기(TT 태스크 주기들의 LCM) |
| **Epoch** | 배포 단위의 모든 노드가 공유하는 hyperperiod 격자의 절대 시간 기준점 |
| **적용 시점(Activation instant)** | 후보 테이블이 활성 테이블이 되는 hyperperiod 경계 |
| **커밋 창(Commit window)** | 적용 시점 직전의 상한이 있는 구간. 이 구간에는 실행 예정인 TT 슬롯이 없으며, 노드는 이 구간에서 이전 테이블을 새 테이블로 전환한다. |
| **잡(Job)** | 태스크의 실행 1회. TT 슬롯 인스턴스 1개, 또는 CBS 예산으로 처리되는 릴리스 1개. *잡 누락*은 실행되어야 했으나 실행되지 않은 인스턴스를 뜻한다. |
| **갱신 트랜잭션** | 갱신 요청 수락부터 새 테이블 활성화 또는 롤백 완료까지의 전체 시퀀스 |
| **롤백(Rollback)** | 실패한 갱신을 노드 안에서 되돌려 이전 테이블이 계속 실행되게 하는 처리. 새 테이블로 전환하기 전의 실패는 준비한 후보를 버리는 **중단(abort)** 으로, 전환한 뒤의 실패는 이전 테이블로 돌아가는 **복원(restore)** 으로 처리한다. |
| **되돌리기(Revert)** | Timpani-O가 이전 내용의 테이블을 새 테이블 식별자로 다시 배포하는 것. 노드에게는 롤백이 아니라 새 갱신이다. |
| **변경 대상 워크로드(Affected workload)** | 갱신으로 인해 슬롯, 예산, CPU 할당, 존재 여부가 바뀌는 워크로드 |
| **무관 워크로드(Unaffected workload)** | 갱신 전후로 동일하게 존재하는 워크로드 |
| **복원 실패 정지 상태(`RESTORE_FAILED`)** | 갱신이 실패하고 이전 테이블도 복원할 수 없을 때 노드가 들어가는 상태. 실행 중인 테이블이 의도 테이블과 일치한다고 보장할 수 없으므로 변경 대상 워크로드의 디스패치를 멈춘다. 벗어나는 유일한 경로는 Timpani-O의 전체 테이블 재적용 성공이다. 일반적인 노드 건강 상태가 아니라 갱신 트랜잭션의 상태이다(§1.4). 안전 분야에서 "degraded"는 기능을 줄여 계속 동작하는 상태를 뜻하므로 이 이름을 쓰지 않는다. DDR-011 v2.x 문서 세트는 비슷한 상태를 `DEGRADED`라고 부른다. |
| **결과 코드(Result code)** | 갱신 시도의 결과를 Timpani-O에 알리는 기계 판독용 값. 최소한 적용, 변경 없음, 거절, 롤백 완료, 복원 실패를 구분한다. |
| **노드 적용 적합성 확인(Node-side applicability check)** | Timpani-N이 수신 테이블의 대상 노드·요청 식별자·인가된 통신 연결, 필드·값의 형식과 표현 가능 범위, 노드 로컬 참조(CPU·태스크 등)의 유효성, 필요한 로컬 자원 및 현재 시계·활성 시간 격자와의 호환성·적용 경계·인계 준비 조건을 활성화 전에 확인하는 것. Timpani-O가 수행한 배치·슬롯 충돌·CPU 할당·CBS 예산 배분 또는 전체 스케줄 가능성 분석을 반복하지 않는다. |
| **테이블 식별자** | 요청과 결과를 상호 연결하기 위해 테이블 버전을 유일하게 식별하는 값 |
| **생성 스케줄(Generated schedule)** | Timpani-O가 생성하여 보유하는 schedule table |
| **전송 표현(Transport representation)** | 테이블이 Timpani-O에서 Timpani-N으로 전달될 때의 형태 |
| **실행 표현(Enforcement representation)** | 커널이 테이블을 실행하고 애플리케이션이 자기 파라미터를 읽을 수 있도록 Timpani-N이 유지하는 형태 |

## 3. 이해관계자와 요구

아래는 전체 단계의 이해관계자 요구이다. Phase 0에서는 §1.5의 시험 경계와 최소 동작을 적용한다.

| 이해관계자 | 요구 |
|:--|:--|
| **Pullpiri(배포 오케스트레이터)** | 차량을 운행에서 내리지 않고 언제든 L1/L2 워크로드를 배포하거나 배포 해제하고, FFI를 성립시키는 노드별 격리 CPU 리스트를 공급하며, 수락/거절에 대한 확정적 응답을 받는다. |
| **Timpani-O(schedule table 생성자)** | 전달받은 워크로드 정보와 격리 CPU 리스트로부터 schedule table을 생성하고 스케줄 가능성을 판단하는 유일한 주체로 남으며, 모든 노드의 실제 적용 상태를 파악한다. |
| **Timpani-N(노드 실행자)** | 전달받은 테이블의 대상·표현·노드 로컬 실행 조건만 확인한다. 배치, 슬롯 간 충돌, CPU 할당, CBS 예산 배분 등 스케줄 가능성을 재계산하지 않고, 테이블을 지정된 CPU에서 지정된 순서대로 실행한다. |
| **Safety(L1/L2) 애플리케이션** | 자신과 무관한 변경에 방해받지 않고, 자신의 타이밍 파라미터가 바뀔 때에는 정의된 방식으로 통보받는다. |
| **기능안전 담당자** | 다른 워크로드의 추가/제거로 인해 무관 safety 워크로드가 데드라인을 놓칠 수 없다는 증거(FFI) |
| **통합/운영 담당자** | 무엇이 요청되었고, 무엇이 적용되었으며, 언제 적용되었고, 왜 실패했는지를 관측한다. |

## 4. 운영 시나리오

각 시나리오는 **전체 단계 완료 시의 동작**을 기술한다. Phase 0에서는 UC-01..UC-04(UC-03의 복구 STOP 제거 포함)의 정상 경로를 §1.5의 제한 조건에서 확인하며, UC-05와 hyperperiod 변경·CBS는 제외한다. 아래 예외 중 기본 입력 거절은 Phase 0, 중복·충돌 관리는 Phase 1, 활성화 실패·단절·다중 노드 부분 실패 복구는 Phase 2에 해당한다.

### UC-01 — Schedule table 전체 대체 (UPD-REPLACE)

- **트리거:** 새로운 워크로드 집합이 유효해지고(예: 주행 모드 전환 Parking → Highway), Pullpiri가 새 워크로드 정보를 제공하면 Timpani-O가 해당 노드용 새 schedule table을 생성한다.
- **전제조건:** 노드가 활성 테이블을 보유하고 실행 중이다.
- **주 흐름:** Timpani-O가 스케줄 가능성을 확인하고 새 테이블 생성 → Timpani-N이 수신 대상·표현·노드 로컬 실행 조건을 확인(스케줄 가능성은 재계산하지 않음) → 적합하면 다음 hyperperiod 경계에서 실행 → 결과 보고
- **후행조건:** 노드는 새 테이블만 실행한다. hyperperiod, 슬롯 배치, CBS 예산 집합이 모두 바뀔 수 있다.
- **특이 성질:** hyperperiod가 변경될 수 있으며, 노드는 공통 epoch 정렬을 잃지 않고 타이밍 격자를 재정렬해야 한다.
- **예외:** E-01(실현 불가), E-02(커밋 실패), E-03(연결 단절)

### UC-02 — 동작 중인 테이블에 워크로드 추가 (UPD-ADD)

- **트리거:** Pullpiri가 이미 워크로드가 동작 중인 노드에 워크로드를 추가 배포한다.
- **전제조건:** 노드에 비어 있지 않은 활성 테이블이 있고, 새 워크로드를 수용할 여유가 있다.
- **주 흐름:** Timpani-O가 배치와 스케줄 가능성을 결정해 결과 테이블 생성 → Timpani-N이 수신 대상·표현·노드 로컬 실행 조건을 확인(배치·스케줄 가능성은 재계산하지 않음) → 적합하면 다음 hyperperiod 경계에서 실행 → 결과 보고
- **후행조건:** 새 워크로드가 디스패치되고, 기존 워크로드는 타이밍 파라미터를 유지한 채 중단 없이 계속된다.
- **예외:** E-01(배치 불가 → 요청 거절, 활성 테이블 불변), E-04(이미 존재하는 워크로드)

### UC-03 — 동작 중인 테이블에서 일부 워크로드 제거 (UPD-REMOVE)

- **트리거:** Pullpiri가 워크로드의 배포를 해제하거나(배포 해제 인터페이스는 OI-17), 복구 결정에 따라 워크로드에 STOP이 적용된다(DDR-012). STOP의 경우 Pullpiri는 노드의 런타임 정리 성공 결과를 Timpani-O를 통해 확인한 뒤 워크로드(컨테이너) 정리를 진행한다.
- **전제조건:** 제거 대상 워크로드가 활성 테이블에 존재하고, 제거 후에도 최소 하나의 워크로드가 남는다.
- **주 흐름:** Timpani-O가 제거 의도를 보존하며 해당 워크로드를 제거한 결과 테이블 생성 → Timpani-N이 수신 대상·표현·노드 로컬 실행 조건을 확인(스케줄 가능성은 재계산하지 않음) → 적합하면 다음 hyperperiod 경계에서 실행하고 제거된 워크로드의 Timpani 런타임 상태를 정리(OS CPU scheduling policy/affinity는 변경·복원하지 않음) → N→O(및 STOP 시 Pullpiri)로 결과 보고
- **후행조건:** 제거된 워크로드는 더 이상 디스패치되지 않고 잔존 런타임 상태를 갖지 않으며, 남은 워크로드는 중단 없이 계속된다.
- **예외:** E-04(존재하지 않는 워크로드), E-02(커밋 실패), E-05(해당 워크로드를 소유하지 않은 노드에 제거 요청 도달)

### UC-04 — Schedule table 전체 삭제 (UPD-CLEAR)

- **트리거:** 마지막 워크로드의 배포가 해제되거나(OI-17), 노드가 드레인되거나, 전체 워크로드 집합이 철거된다.
- **전제조건:** 노드가 활성 테이블을 보유한다.
- **주 흐름:** Timpani-O가 해당 노드용 빈 테이블을 생성·검증 → Timpani-N이 빈 테이블도 노드 적용 적합성 확인을 수행(현재 시계·활성 시간 격자·적용 경계·인계 준비 조건 포함, 스케줄 가능성은 재계산하지 않음) → 적합하면 다음 hyperperiod 경계에서 실행하고 모든 TT 슬롯 트리거와 CBS 예산 통제를 중단하며 워크로드 관련 런타임 상태를 반환 → 결과 보고
- **후행조건:** 노드는 **비어 있지만 유효한** 테이블을 보유하고 TT/CBS 관점에서 유휴 상태이며, 후속 UPD-REPLACE 또는 UPD-ADD를 즉시 수용할 수 있다.
- **특이 성질:** 빈 테이블은 "갱신 없음"이 아니라 **정당한 테이블**이다. 조용히 무시되어서도 안 되고, 이전 테이블이 계속 실행되도록 남겨서도 안 된다.

### UC-05 — 동작 중인 워크로드의 파라미터 변경 (UPD-MODIFY)

- **트리거:** 이미 동작 중인 워크로드의 타이밍 파라미터가 바뀐다 — 주기·CBS 예산·데드라인은 Pullpiri를 통해, CPU 할당은 Timpani-O의 재배치를 통해 — 워크로드 추가·제거는 없다.
- **전제조건:** 해당 워크로드가 활성 테이블에 존재하고, 변경된 파라미터가 실현 가능하다.
- **주 흐름:** Timpani-O가 변경 파라미터를 반영해 스케줄 가능성을 판단하고 결과 테이블 생성 → Timpani-N이 수신 대상·표현·노드 로컬 실행 조건을 확인(스케줄 가능성은 재계산하지 않음) → 적합하면 다음 hyperperiod 경계에서 실행 → 해당 워크로드가 새 파라미터로 계속 동작하고 결과 보고
- **후행조건:** 변경된 워크로드는 재시작 없이 새 파라미터로 동작하고, 워크로드 집합은 변하지 않으며, 다른 워크로드는 영향을 받지 않는다.
- **특이 성질:** 워크로드가 변경 구간을 가로질러 계속 동작하므로, 애플리케이션 가시 파라미터는 재등록이 아니라 재해석되어야 한다.
- **예외:** E-01(새 파라미터 실현 불가), E-04(존재하지 않는 워크로드)

## 5. 요구사항

우선순위: **M** = 해당 단계 수용을 위한 필수, **S** = 권고, **C** = 조건부/향후

**단계 표기:** `0`, `1`, `2`는 적용 단계이며, `0/1`처럼 여러 단계가 있으면 해당 ID를 단계적으로 충족한다. **Phase 0은 §1.5.3의 내용만 적용**한다. `1`, `2`, `1/2` 항목은 현재 구현·수용의 선행 조건이 아니다. 아래 원문은 후속 단계까지의 목표를 보존한 목록이며 현재 설계의 상세 입력으로 일괄 사용하지 않는다.

> 요구사항 ID는 한 번 부여되면 재번호 부여나 재사용을 하지 않는다. 따라서 절 내에서 ID가 연속하지 않을 수 있으며 이는 오류가 아니다.
>
> **ID 접두어 변경(2026-10-01).** DDR-011 v2.3 SRS가 `REQ-RTU-F/N-###`을 다른 의미로 쓰므로, 본 문서의 접두어를 `REQ-RTU-`에서 `REQ-011-`로 바꾸었다. 번호는 바꾸지 않았다. 본문의 `F-###`, `N-###`은 각각 `REQ-011-F-###`, `REQ-011-N-###`의 약칭이다.

### 5.5 생성 검증과 노드 적용 적합성 확인

> **책임 경계.** 스케줄 가능성은 Timpani-O가 판단한다. Timpani-N의 확인은 수신·표현 오류와 노드 로컬 적용 불가 조건을 활성화 전에 걸러내는 데 한정한다. Timpani-N은 슬롯 배치·중첩 분석, CPU 재할당, CBS 예산 배분 또는 전체 스케줄 가능성 검사를 다시 수행하지 않는다. 아래 노드 측 검사는 요구사항이며, 현행 구현이 이미 이를 모두 수행한다는 뜻은 아니다.

## 7. 수용 기준(요구사항 수준)

### 7.1 현재 수용 기준 — Phase 0

§1.5의 시험 조건에서 아래 항목을 모두 만족하면 **Phase 0만 완료**한 것으로 판단한다. SRS-011은 이를 시험 입력·관측점·성공/실패 판정으로 구체화한다. 목표 하드웨어에서 실제 실행을 확인하며, 성능 상한이나 fail-safe 보장을 입증한 것으로 해석하지 않는다.

| **AC-14** | 하나의 논리적 변경이 여러 노드에 걸치고 한 노드가 거절·실패할 때, 모든 노드의 결과 상태가 문서화된 다중 노드 원자성 경계와 일치하고 Timpani-O에 보고된다. | F-018, F-047, F-033 |
| **AC-15** | 복원 불가 활성화 실패를 주입하면 노드가 구분된 결과 코드를 보고하고, 변경 대상 워크로드의 디스패치를 중단하며, 증분 갱신은 거절하고, 전체 테이블 재적용으로 의도 테이블과 일치하는 상태로 복귀한다. | F-030, F-048, F-049 |

### 8.2 하위 추적

현재 개정의 추적 대상은 **§1.5.3의 Phase 0 적용 내용과 AC-P0-01..AC-P0-08**이다. §5의 63개 요구사항 ID는 전체 목표 목록으로 보존하되, Phase 1/2 항목은 이관 목록에만 남기고 현재 활성 요구사항·구현 작업으로 전개하지 않는다. 여러 단계에 걸친 ID는 현재 충족하는 부분과 남은 부분을 구분한다.

| 문서 | Phase 0 개정 기준 |
|:--|:--|
| **SRS-011** | Phase 0 적용 요구사항과 수용 기준만 활성화하고 시험 조건·최소 거절·적용/결과 판정을 구체화. 전체 63개 항목의 동시 구체화를 요구하지 않음 |
| **HLD-011** | 정상 갱신의 입력→O 생성/검증→전송→N 준비→경계 적용→결과 보고와 RT/비RT 책임 경계에 한정 |
| **DDR-011** | Phase 0에 필요한 결정만 기록. 기존 고급 설계 결정은 현재 채택·후속 이관·비적용을 구분하고 존재만으로 구현 의무를 만들지 않음 |
| **LLD-011** | 위 정상 경로의 자료·인터페이스 사용·동기화·기본 오류 처리만 상세화. 복구 상태 기계·CBS·대기/병합 알고리즘 제외 |
| **implementation_plan** | Phase 0 구현·시험 작업만 실행 계획으로 분해하고 각 작업을 활성 SRS 및 AC-P0 항목에 연결. Phase 1/2는 후속 목록으로 분리하며 선행 완료 조건으로 연결하지 않음 |

추적 방향은 **REQ-011(Phase 0 적용 부분) → SRS-011 → HLD/DDR/LLD → implementation_plan 및 시험**이다. 각 후속 문서는 적용 단계를 명시해야 한다(SHALL). 현재 문서 개정이 끝나기 전까지 기존 문서의 포괄적 SHALL·전체 수용 기준·이전 버전 해석을 Phase 0의 범위 확대 근거로 사용하지 않는다.

SRS의 활성 요구사항은 상위 REQ-011 ID와 AC-P0 항목을 인용하고, 설계 결정·구현 작업도 이 연결을 유지해야 한다. 폐기·이관된 ID는 재사용하지 않으며 접두어는 구분한다(REQ-011은 `REQ-011-`, SRS-011은 `REQ-RTU-`). Phase 1/2 착수 시 해당 이관 항목을 활성화하고 추적 매트릭스를 확장한다. **이번 수정은 REQ에 한정하며 후속 문서 자체의 개정 완료를 뜻하지 않는다.**
