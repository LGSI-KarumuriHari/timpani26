# OVERVIEW-011: Runtime Table Update 디자인 개요

**작성일:** 2026-11-11  
**상태:** Draft  
**현재 설계 기준:** Phase 0 — Runtime Table Update 기본 동작 확인  
**관련 문서:** [REQ-011](REQ-011-runtime-table-update.md), [SRS-011](SRS-011-runtime-table-update.md), [HLD-011](HLD-011-runtime-table-update.md), [DDR-011](DDR-011-runtime-table-update.md), [LLD-011](LLD-011-runtime-table-update.md)

---

## 1. 무엇을 해결하는 기능인가?

차량이나 실시간 시스템이 동작하는 중에도 주행 모드가 바뀌거나, 새로운 기능이 추가되거나, 문제가 생긴 워크로드를 멈춰야 하는 상황이 발생한다.

**Runtime Table Update(런타임 스케줄 테이블 갱신)** 는 시스템을 멈추지 않고 실행 중인 노드의 스케줄 테이블을 안전하게 바꾸는 기능이다. 핵심 목표는 세 가지다.

- **무중단 실행:** Timpani-O, Timpani-N 데몬은 물론, 변경 대상이 아닌 기존 워크로드도 재시작하지 않고 그대로 실행을 이어간다.
- **깔끔한 일괄 전환:** 이미 시작된 작업을 중간에 자르지 않고, 정해진 주기 경계(Hyperperiod 경계)에서 이전 테이블에서 새 테이블로 한 번에 전환한다. 두 테이블이 섞여서 실행되는 일은 없다.
- **명확한 역할 분리:** 스케줄 계산과 배치는 오직 중앙의 **Timpani-O**만 담당한다. 각 노드의 **Timpani-N**은 전달받은 테이블이 해당 노드에서 실행 가능한지만 확인한 뒤 정해진 시각에 그대로 실행한다.

---

## 2. 어떤 변경을 지원하는가?

실제 운영에서 발생하는 스케줄 변경은 다섯 가지로 정리된다.

| 변경 종류 | 직관적 의미 | 예시 상황 | 적용 단계 |
|:--|:--|:--|:--|
| **전체 대체 (REPLACE)** | 스케줄 테이블 전체를 새 테이블로 교체 | 주차 모드 → 고속주행 모드 전환 | Phase 0 / 1 |
| **워크로드 추가 (ADD)** | 기존 워크로드는 그대로 두고 새 워크로드만 추가 | 동작 중인 노드에 신규 앱 추가 배포 | Phase 0 |
| **워크로드 제거 (REMOVE)** | 일부 워크로드만 빼고 나머지는 그대로 유지 | 특정 앱 배포 해제, 결함 워크로드 정지(`STOP`) | Phase 0 |
| **전체 삭제 (CLEAR)** | 모든 워크로드를 내려 노드를 빈(유휴) 상태로 전환 | 노드의 모든 실시간 작업 철수 후 대기 | Phase 0 |
| **파라미터 변경 (MODIFY)** | 워크로드 목록은 유지한 채 주기·예산·CPU만 변경 | 실행 중인 작업의 타이밍 조건 조정 | Phase 1 |

> **설계 포인트 — 전달 방식은 언제나 '전체 테이블(Full Snapshot)' 하나**  
> 의미상으로는 "추가"나 "제거"지만, 노드에는 복잡한 부분 수정 명령 대신 **변경이 반영된 완성본 테이블 전체**를 보낸다. 결함 복구로 특정 워크로드를 멈출 때(`RECOVERY_STOP`)도 별도의 정지 신호로 노드에서 직접 지우지 않고, 해당 워크로드를 제외한 새 전체 테이블을 보내 동일한 방식으로 안전하게 전환한다.

## 3. 왜 단계(Phase 0 / 1 / 2)를 나누어 진행하는가?

처음부터 다중 노드 동기화와 모든 장애 복구까지 한꺼번에 구현하면 복잡도가 지나치게 커진다. 따라서 기능을 세 단계로 나누어 순차적으로 완성하며, **현재 011 문서 세트의 설계 기준은 Phase 0**이다.

| 단계 | 핵심 목표 | 다루는 범위 |
|:--|:--|:--|
| **Phase 0 (현재 기준)** | **기본 전환 동작 확인** | 단일 노드 · 사전 지정된 하나 이상의 격리 CPU(유지 활성 태스크는 기존 배정 코어에 고정) · L1(TT) 워크로드 · 고정된 시간 기준에서 대체/추가/제거(복구 `STOP` 포함)/전체 삭제의 무중단 경계 전환과 기본 입력 거절 확인 |
| **Phase 1** | **기능 확장 및 품질 확보** | L2(CBS) 워크로드, 파라미터 변경(MODIFY) 및 활성 태스크의 코어 간 이동, 주기·격리 CPU 구성 변경, 코어별 타이머 확장·다중 노드 확장, 동시 요청 대기·병합, 정량적 지터·지연 상한 검증 |
| **Phase 2** | **Fail-Safe (장애 및 안전 복구)** | 전환 도중 실패 시 자동 롤백 및 안전 정지, 통신 단절·재시작 후 자동 재동기화, 시계 이상 대응, 결함 누적 기록 보존 |

## 4. 누가 어떤 역할을 맡는가?

```mermaid
flowchart LR
    P["상위 오케스트레이터 / 입력<br/>(Pullpiri 등)"] -->|"워크로드 변경 / STOP 요청"| O["Timpani-O<br/>(스케줄 생성 및 검증)"]
    O -->|"새 전체 테이블 전송"| N["Timpani-N 비실시간 경로<br/>(사전 점검 · 대기 공간 준비 · 정리)"]
    N -->|"전환 준비 완료"| RT["Timpani-N 상주 타이머 & BPF<br/>(주기 경계에서 즉시 전환)"]
    RT -->|"슬롯 신호 & 공유 메모리 게시"| APP["실시간 애플리케이션<br/>(libttsched)"]
    N -->|"실제 적용 완료 보고 (ACK)"| O
```

- **상위 오케스트레이터 (Pullpiri 등):** 어떤 워크로드를 실행하거나 멈출지 결정해 요청한다. 결함으로 워크로드를 멈출(`STOP`) 때는 노드의 스케줄 정리가 끝났다는 응답을 확인한 뒤에 컨테이너를 종료한다.
- **Timpani-O (유일한 스케줄 생성자):** 현재 확정된 모델을 바로 덮어쓰지 않고 별도의 '후보 테이블'을 만들어 스케줄 가능성을 검증한다. 노드가 실제 경계에서 적용을 마쳤다고 보고한 뒤에야 후보를 확정 상태로 반영한다.
- **Timpani-N 비실시간(Non-RT) 경로:** 무거운 준비와 뒷정리를 전담한다. 입력이 유효한지 사전 확인하고, 현재 실행에 영향을 주지 않는 대기 공간에 새 설정을 준비하며, 전환이 끝나면 이전 자원을 정리하고 결과를 보고한다.
- **Timpani-N 실시간(RT) 타이머 & 커널(BPF):** 실시간 경로에서는 메모리 할당, 맵 작성, 네트워크 통신, 로그 출력을 하지 않는다. 미리 준비된 설정을 주기 경계 시각에 가벼운 스위치 전환만으로 활성화한다.
- **실시간 애플리케이션 (`libttsched`):** 공유 메모리에 게시된 테이블을 읽고 동작한다. 테이블이 교체되는 과도기 데이터를 읽지 않으며, 실제 자기 실행 차례일 때만 작업을 수행한다.

## 5. 멈추지 않고 테이블을 갈아끼우는 원리

실행 중인 작업을 방해하지 않고 테이블을 교체하기 위해 **이중 공간 준비(Double Buffering)** 와 **주기 경계 전환**을 결합한다.

```mermaid
flowchart LR
    S1["1. 이전 테이블 실행 중<br/>(뒤에서 새 설정 미리 준비)"] --> S2["2. 마지막 작업 완료 후 여유 구간<br/>(잠시 진입 닫고 전환 대기)"]
    S2 --> S3["3. Hyperperiod 경계 도달<br/>(새 설정·공유 메모리 동시 활성화)"]
    S3 --> S4["4. 새 테이블 실행 시작<br/>(이전 자원 정리 후 완료 보고)"]
```

### 1단계: 후보 검증 및 뒤에서 미리 준비
Timpani-O가 기존 활성 태스크는 원래 코어에 고정하고 신규 워크로드만 빈 코어(또는 최소 부하 코어)에 배정해 새 테이블을 보내면, Timpani-N은 대상 노드·필수 값·격리 CPU 집합·태스크별 코어 고정 여부가 유효한지 먼저 확인한다. 단일 태스크가 여러 코어에 걸치거나 기존 태스크의 코어가 바뀌는 등 문제가 있으면 즉시 거절하여 현재 실행 중인 테이블을 안전하게 지킨다.

문제가 없으면 커널(BPF)의 **두 벌 공간(현재 실행용 / 다음 대기용)** 중 비어 있는 대기용 공간에 새 슬롯과 태스크별 배정 CPU 정보를 채우고, 애플리케이션에 보여줄 새 공유 메모리 화면도 미리 만들어 둔다. (한 번에 1건의 갱신만 처리하며, 진행 중 들어오는 추가 요청은 거절한다.)

### 2단계: 여유 구간(TT-free 구간)에서 인계 대기
사용 중인 모든 격리 코어에서 현재 주기의 마지막 작업 슬롯이 끝난 뒤부터 다음 주기 경계 전까지의 공통 빈 시간(TT-free 구간)을 기다린다. 모든 관여 코어에서 진행 중이던 작업이 끝난 것을 확인하면 새로운 작업이 중간에 끼어들거나 다른 격리 코어로 흘러가지 않도록 문을 닫고 배정 코어별로 대기시키며, 공유 메모리를 '갱신 중' 상태로 표시해 앱이 반쪽짜리 정보를 읽지 못하게 한다. 만약 준비가 늦어지면 무리하게 적용하지 않고 다음 주기 경계로 미룬다.

### 3단계: 주기 경계(Hyperperiod 경계)에서 한 번에 스위치 전환
정확히 다음 주기가 시작되는 경계 시각이 되면, 멈추지 않고 계속 돌아가던 상주 타이머가 **대기용 커널 설정 활성화, 공유 메모리 유효화, 작업 실행 허용**을 한 번에 연다. 덕분에 경계 전까지는 이전 테이블만, 경계 이후부터는 새 테이블만 정확히 실행된다. 전체 삭제(`CLEAR`)일 때도 타이머는 멈추지 않고 빈 테이블 상태로 주기만 유지하며 다음 갱신을 기다린다.

### 4단계: 애플리케이션 보호 및 정리 후 완료 보고
- **애플리케이션의 오작동 방지:** 공유 메모리는 세대 번호를 이용해 완전히 게시된 상태만 읽게 한다. 또한 테이블 게시 과정에서 깨어나더라도 자기 작업 카운터가 실제로 증가했을 때만 작업으로 실행하므로, 가짜 실행(오발화)이 일어나지 않는다. 유지되는 워크로드는 기존 위치와 카운터를 그대로 이어받는다.
- **정리 후 성공 보고:** 경계 전환이 실제로 끝난 것을 확인한 뒤, 비실시간 경로에서 제거된 워크로드의 Timpani 내부 등록 정보만 깔끔히 정리한다(프로세스의 OS 스케줄링 정책이나 CPU 친화도는 건드리지 않음). 이 과정까지 모두 끝나야 Timpani-O에 **적용 성공(ACK)** 을 보낸다.

## 6. 핵심 안전 원칙과 현재 한계

- **실시간 경로의 순수성 유지:** 타이머 스레드를 갱신 때마다 껐다 켜지 않으며, 실시간 루프 안에는 블로킹 락이나 동적 메모리 할당, I/O 작업을 일절 두지 않는다.
- **'전송 완료'와 '적용 완료'의 엄격한 구분:** 노드가 메시지를 받았거나 준비만 마친 시점에는 성공으로 보고하지 않는다. 반드시 주기 경계에서 실제 전환과 정리가 끝난 뒤에 성공을 확정한다.
- **Phase 0의 명확한 한계:** 현재 단계(Phase 0)는 정상적인 경계 전환과 사전 거절이 올바르게 동작하는지 검증하는 단계다. 만약 전환이 이미 시작된 도중에 오류가 나거나 네트워크가 끊기면 자동 복구를 시도했다고 가정하지 않고 즉시 시험을 멈추어 원인을 기록한다(자동 롤백과 재연결 복구는 Phase 2에서 구현).
